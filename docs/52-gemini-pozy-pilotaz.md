  Dokumentacja structured output używa go w przykładach. Alternatywa do porównania: `gemini-3.1-pro-preview` (najnowszy model „Pro”, wersja preview, myślenie domyślnie high). Tańszy wariant: `gemini-3.8-flash`.

### 6a. Pierwszy przebieg vertex (26.10.2026): 404 „model nie znaleziony lub brak dostępu” — poprawki

Klucz został przyjęty (brak 401/403/429), ale API odpowiedziało 404 dla `gemini-4-argon`; w treści błędu zasób był szukany w `us-central1` (bez projektu w adresie host `aiplatform.googleapis.com` wybrał region według klucza, nie „global”). Karta modelu (…/models/gemini/4-argon) podaje dla Standard PayGo tylko `global` oraz multi-regiony `us` i `eu` — **`us-central1` nie jest obsługiwane**. Wnioski i zmiany:
- Nowy parametr `--lokalizacja global|us|eu` (wejście workflowu `lokalizacja`): `global` = `aiplatform.googleapis.com`, `us` / `eu` = `us-aiplatform.googleapis.com` / `eu-aiplatform.googleapis.com` (multi-regionalne hosty; **nazwa hosta wnioskowana z konwencji nazw, nie z przeczytanej strony — do potwierdzenia przebiegiem `lista_modeli`**). Identyfikator projektu nadal nie jest używany.
- Nowy tryb bez kosztu `--lista-modeli` (wejście `lista_modeli`, artefakt `modele.json`): `GET /v1beta1/publishers/google/models` (lista Model Garden, strona …/reference/rest/v1beta1/publishers.models/list) oraz `GET /v1/publishers/google/models/<model>` dla każdego z naszych modeli (…/reference/rest/v1/publishers.models/get). Czy klucz API może wołać te metody, dokumentacja nie mówi — wynik 401/403/404 też jest informacją.
- 404 jest twardym stopem (kod 5) po pierwszym błędzie, jak 401/402/403/429.
- Prywatność: treść błędów API zawiera ścieżkę zasobu z numerem projektu, więc `maskuj()` zastępuje `projects/<id>` i długie ciągi cyfr (docs/40, L-035).
- Jeśli `lista_modeli` pokaże, że `gemini-4-argon` jest niedostępny dla klucza (np. klucz ograniczony do trybu express, w którym wg listy modeli Argon nie ma), zostają `gemini-3.1-pro-preview` (jest na liście express) i `gemini-3.8-flash`.

### 6b. Dalsze przebiegi (26.10.2026): lista modeli, region express, 400 „invalid argument”

- **Lista modeli (`lista_modeli`) dała 401 „API keys are not supported by this API”** — `publishers.models.list/get` nie obsługują klucza API (wymagają OAuth); tryb `--lista-modeli` zostaje jako diagnostyka, ale dla kluczy API nie jest źródłem prawdy. Źródłem prawdy jest lista modeli express (poniżej) i próba połączenia.
- **Dlaczego `us-central1` mimo `global`:** przegląd express mode (…/models/start/express-mode/overview) mówi, że w express mode używany jest region wybrany przy rejestracji („the location you selected when signing up in express mode is used throughout your experience”), a adres bez projektu nie pozwala go zmienić. Argon jest wg karty modelu dostępny w Standard PayGo tylko w `global`, `us`, `eu`, a lista modeli express (na tej samej stronie) go **nie zawiera** (zawiera m.in. `gemini-3.1-pro-preview`, `gemini-3-flash-preview`, `gemini-2.5-pro/flash`). Wniosek: **klucz express mode nie dosięgnie `gemini-4-argon`**; dla Argon potrzebny jest zwykły klucz Google Cloud (projekt z rozliczeniami, „Agent Platform API” włączone) — wtedy dokumentacja szybkiego startu (…/models/start?usertype=apikey) pokazuje ten sam adres bez projektu.
- **Wskazanie projektu i lokalizacji w ścieżce z kluczem API** (`/v1/projects/<p>/locations/global/publishers/google/models/<m>:generateContent`): dokumentacja tego dla kluczy API nie opisuje (przewodnik Argon pokazuje tę ścieżkę wyłącznie z tokenem OAuth `Authorization: Bearer`). **Niepotwierdzone**; nie wdrożone (identyfikator projektu musiałby trafić do zmiennej repozytorium). Do rozważenia dopiero, jeśli zwykły klucz nadal nie dosięgnie Argon.
- **Błąd 400 „Request contains an invalid argument” (3.1 Pro Preview, global):** model znaleziony, żądanie odrzucone. Zmiany: (a) 400 w trybie vertex to twardy stop po pierwszym błędzie; (b) w komunikacie i raporcie jest pełne `error.details` (np. `fieldViolations`, nazwa złego pola), zamaskowane; (c) żądanie ma teraz cztery warianty formatu JSON, a próba połączenia wybiera pierwszy przyjęty (400 nie jest rozliczany): `responseJsonSchema` → `responseSchema` (podzbiór OpenAPI: bez `$schema`, `additionalProperties`, `const`, `multipleOf`, `uniqueItems`, wielotypowych `type`) → `responseFormat[]` (nowe pole z dokumentacji GenerationConfig) → sam `responseMimeType` ze schematem w treści polecenia (walidator i tak sprawdza wynik). Wybrany i odrzucone formaty są w `raport.json` (`polaczenie`). Treść żądania sprawdzona z …/reference/rest/v1/GenerationConfig i …/GenerateContentResponse; nadal nie wiadomo, który wariant API przyjmie — rozstrzygnie przebieg.

### 6c. Przebieg 40282417033: próba połączenia OK, właściwe żądanie 400 bez szczegółów

Próba połączenia (trywialny schemat, `responseJsonSchema`) przeszła, rozliczenie działa (≈ 0,0024 USD), ale żądanie z pełnym schematem kontraktu (`schematPozy('pull_up')`, ok. 10 tys. znaków, zawiera `$schema`, `maxLength`, `additionalProperties`, `minItems/maxItems`, `minimum/maximum`, `enum`) dostało 400 bez `fieldViolations`. Przyczyny nie da się ustalić z dokumentacji, więc:
- **Negocjacja formatu w pętli:** przy 400 pierwszego właściwego żądania skrypt (bez kosztu — 400 nie jest rozliczany) próbuje kolejno: `responseJsonSchema` pełny → `responseJsonSchema` uproszczony (bez `$schema`/`$id`/`$comment`, `maxLength`/`minLength`/`pattern`/`uniqueItems`/`multipleOf`) → `responseSchema` OpenAPI → `responseFormat[]` → sam tryb JSON ze schematem w poleceniu. Działający format zostaje do końca przebiegu (`raport.json` → `format`, log: „format JSON zmieniony na …”). Dopiero wyczerpanie wszystkich = twardy stop (kod 5).
- **Tryb `--diagnoza`** (wejście workflowu `diagnoza`, artefakt `diagnoza.json`, ≤ 40 krótkich wywołań z `maxOutputTokens` 256, koszt pod `limit_usd`): pełny schemat w każdym z pięciu formatów; trywialny schemat z `maxOutputTokens` 16000; pełny prompt bez schematu; a gdy pełny `jsonSchema` odrzucony — każda właściwość najwyższego poziomu osobno i schemat bez kolejnych klas słów kluczowych. Log wskazuje, co przechodzi.


## 7. Ręczne generowanie póz w aplikacji Gemini (decyzja właściciela 26.10.2026) — procedura

Powód: API okazało się drogie (ok. 0,40 USD za ćwiczenie, ok. 50% póz przechodzi walidację w pilotażu `pull_up`: 2 z 13 przy przerwanym przebiegu) i Argon nie jest dostępny przez nasz klucz. Pozy generuje **właściciel ręcznie w aplikacji Gemini** (model Argon, w ramach abonamentu), **jedno polecenie na rodzinę ruchu**; walidacja i nakładanie zostają po naszej stronie (te same testy geometrii co w pilotażu API, `scripts/figures/v2-validate.mjs`).

**Generowanie poleceń (agent / koordynator, bez klucza i sieci):** `node scripts/figures/gemini-polecenia.mjs --rodzina <id> --wyjscie <katalog>` albo `--wszystkie` (każda rodzina z docs/51 w stanie „do zrobienia”; gotowe: przysiad, wyciskanie, zawias — pomijane; ćwiczenia z pozą już zapisaną w `lib/figures/v2/poses/<rodzina>.json` też). Powstaje plik `<id>.md` (rodzina do 12 ćwiczeń) albo `<id>-1.md`, `<id>-2.md`… (większe rodziny, równe części). Pliki trafiają do katalogu roboczego, **nie do repozytorium**. Treść polecenia (po polsku — nazwy pól kontraktu są polskie, więc jeden język nie miesza instrukcji z danymi):
